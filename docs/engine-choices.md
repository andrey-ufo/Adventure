# Engine choices

**Status:** stable (Ф4.12, 2026-11-25). Describes the four choice-related
features shipped in Фаза 4: choice templates, disabled/hidden choices,
merge points and atomic subroutines. These are **on-disk constructs**;
changes here are breaking for adventure files.

This is the author-facing and runtime reference for the unified choice
model. It is the companion to:

- [`engine-architecture.md`](./engine-architecture.md) — the module
  structure, IR, parser, runtime and analyzer.
- [`engine-conditions.md`](./engine-conditions.md) — the condition
  grammar used by `condition`, `visibility_condition`, template
  conditions and subroutine step guards.
- [`engine-types.md`](./engine-types.md) — variable types, `TypeChecker`,
  and the type errors referenced below.

## Unified choice model

A `Choice` (IR `com.myapp.adventure.engine.ir.Choice`, JSON object inside
`scenes[].choices[]`) has:

| Field | JSON | Meaning |
|---|---|---|
| `id` | `id` (optional) | Stable choice id; generated by the editor/parser if absent. |
| `text` | `text` | Button label / prose shown to the player. |
| `nextScene` | `next_scene` | Target scene. For a subroutine call this is the **return target**. `@self` is legal only in a `ChoiceTemplate`. |
| `condition` | `condition` | "Can the player pick this?" — false → visible but **disabled**. |
| `visibilityCondition` | `visibility_condition` | "Is this choice shown at all?" — false → **hidden**. |
| `effects` | `set_flags`, `remove_flags`, `modify_stats` | State changes applied when picked. |
| `templateRef` | `template_ref` | Editor metadata: this expanded choice came from a template. Runtime ignores it. |
| `call` | `call` | Optional atomic subroutine call (Ф4.7). |

### Execution order (`Engine.step`)

1. **Current scene** exists, otherwise `Rejected(SceneNotFound)`.
2. **Choice** exists in that scene, otherwise `Rejected(ChoiceNotFound)`.
3. **Blockers**: `choice.condition` and the scene's step gate are
   collected. Any blocker → `Rejected(Blocked(blockers))`. Condition
   blockers come before the temporary gate blocker.
4. **Target scene** exists, otherwise `Rejected(SceneNotFound)` — checked
   before effects so nothing is applied into a void.
5. Apply `choice.effects`.
6. If `choice.call` is present, execute the subroutine **atomically**
   (see §Subroutines).
7. Evaluate invariants against the post-call state; `outcome` may be
   `Death` (or a future outcome).
8. Return `Success(state, currentScene, outcome, disabledChoices)`.

The **reader** then applies the target scene's effects on first entry
(`appliedSceneEffects`), re-evaluates invariants, handles the gate/ending
flow and saves progress. Scene effects are not applied by `Engine.step`:
re-entering a scene must not re-drain health.

**Visibility is not checked by `Engine.step`.** A hidden choice is a UI
concern: `Evaluator.choiceState` says `Hidden`, the reader does not render
it. If a stale UI somehow calls a hidden choice, the engine still runs it
(only `condition` and the gate are runtime blockers).

## Disabled vs hidden (N4 / Ф4.4)

`Evaluator.choiceState(choice, state)` is the single source of truth for
the button's display state:

| State | When | UI |
|---|---|---|
| `Visible` | shown and pickable | normal button |
| `Disabled(reason)` | `visibilityCondition` true/pass, `condition` false/fails | shown, greyed out, not clickable |
| `Hidden` | `visibilityCondition` false/fails | not rendered at all |

**Hidden wins over Disabled (decision G1).** If both conditions are false,
the state is `Hidden`: "do not show this at all" is stronger than "show it
disabled". A reason for a hidden button would never be rendered.

`reason` is a structured `Reason` (has/compare/in-range/not/and/or
failures). Since the Ф4 gate the reader formats a short localized
reason ("Недоступно: нужно: potion >= 2 (сейчас 1)") via
`formatChoiceDisabledReason`; `And`/`Or` compose recursively. The
scene gate has its own line ("Сначала пройдите шаги"). Hidden choices
still render nothing — they have no button to explain.

**Scene gate.** `Scene.gate` is scene-level, not per-choice. While the gate
is active the reader disables **all** choices uniformly; it is not part of
`ChoiceState`. `Engine.step` receives `stepsInScene` and adds
`Blocker.GateNotPassed(remaining)` if the gate has not been passed.

### `StepResult.Success.disabledChoices`

After a successful step, the result includes the visible-but-disabled
choices of the **target scene**, computed against the post-step state:

```kotlin
data class DisabledChoice(val choiceId: ChoiceId, val reason: Reason)
```

- hidden choices are excluded;
- enabled choices are excluded;
- the scene gate is not duplicated here;
- a subroutine that sets a flag is reflected immediately.

The Compose reader still renders from `getChoiceStates()`; the field is an
API convenience for non-Compose runtimes and tools.

## Choice templates (Ф4.1–Ф4.3, N3)

A template is a reusable **button recipe** declared once in
`choice_templates` and instantiated in any number of scenes.

```json
"choice_templates": [
  {
    "id": "rest",
    "parameters": [],
    "text": "Отдохнуть через шаблон rest (+5 здоровья)",
    "visibility_condition": "health < 100",
    "modify_stats": { "health": 5 },
    "next_scene": "@self"
  }
]
```

Instantiation is **expansion**: the editor (or `applyTemplate`) writes a
fully expanded ordinary choice plus a `template_ref` metadata object:

```json
{
  "text": "Отдохнуть через шаблон rest (+5 здоровья)",
  "next_scene": "start",
  "visibility_condition": "health < 100",
  "modify_stats": { "health": 5 },
  "template_ref": { "template_id": "rest", "args": {} }
}
```

The runtime never looks at `template_ref` or `choice_templates`; it sees
only the expanded fields. `template_ref` is for the editor ("this came
from template X", 📦 badge, future update-all).

### Substitution

`applyTemplate(template, args, choiceId)` takes `args: Map<String, String>`
(parameter name → actual variable name):

1. **Text** — `{paramName}` in `template.text` is replaced with the arg
   value. Braces distinguish parameters from prose.
2. **AST name slots** — exact parameter-name matches in `Condition.Has`,
   `Condition.VarRef`, `Condition.Compare.varName`,
   `Condition.InRange.varName`, `Effect.SetFlag`, `Effect.RemoveFlag`,
   `Effect.ModifyStat.name`, `Effect.Set.name` are replaced by the arg
   value; non-matching names remain global variable references.
3. **Integer slots** (`value`, `delta`, `min`, `max`) are **not**
   parameterizable in Ф4. This is a deliberate limitation; use separate
   template variants or an effect with a fixed delta.
4. **`next_scene`** is copied verbatim, except `@self`
   (`ChoiceTemplate.SELF`) which resolves to the scene where the template
   is applied. A non-template choice with `next_scene: "@self"` is a
   dangling reference (`CompileError.MissingNextScene`).

Template definitions are **not type-checked today**
(`TypeChecker.checkChoiceTemplate` is deferred): only the expanded
choices are checked against the global variable table. Placeholder typos
in template text survive expansion literally; the realtime linter (Ф9.2)
is the intended home for that check.

**Editing a template does not auto-update existing expanded choices.**
"Update all uses" is not implemented. The `template_ref` metadata is kept
so it can be added later.

## Merge points (Ф4.5–Ф4.6, N5)

A merge point is a scene where branches deliberately converge. It is an
**explicit scene attribute**, not a separate IR node:

```json
{
  "id": "merge_test",
  "text": "...",
  "merge": true,
  "merge_sources": ["health_test", "items_test"],
  "choices": [{ "text": "Назад", "next_scene": "start" }]
}
```

- `merge` (default `false`) — the scene declares itself a convergence
  point.
- `merge_sources` (default `[]`) — the branches the author says lead here.
  Empty is allowed: the analyzer can collect incoming `next_scene` edges.

**Runtime has no special merge operation.** `Engine.step` already applied
the chosen branch's effects (and any subroutine outputs) before entering
the merge scene; the arriving `PlayerState` is the accumulated pre-branch
state plus that branch's delta. Nothing is copied/diffed at the merge
point. True per-branch delta tracking belongs to Ф5.

Validation split:

- **Compile** — every `merge_sources` id must exist
  (`CompileError.MissingMergeSource`).
- **Analyzer** — `Analyzer.checkMerges` emits three `MergeConflict`
  warnings:
  - `NoIncomingBranches` — `merge: true`, but no choice leads here;
  - `SourceDoesNotLeadHere` — a declared source has no edge to the merge
    scene;
  - `SourceNotReachable` — a declared source leads here but is not
    reachable from `start_scene` (only when the merge itself is reachable,
    so `UnreachableScene` is not duplicated).
- **Not analyzed yet** — state compatibility between branches needs Ф5
  deltas.
- **Editor** — "Точка слияния" checkbox in scene settings, optional
  source list with a scene picker; a map-style visual join is future
  polish.

## Subroutines (Ф4.7–Ф4.9, N6.base)

A subroutine is a reusable **atomic procedure**: it runs to completion
inside one `Engine.step`. The player never sees intermediate screens, no
save can happen mid-call, and undo returns to the state before the
invoking choice.

```json
"subroutines": [
  {
    "id": "drink_potion",
    "inputs": [
      { "name": "item", "type": "item_count" },
      { "name": "health", "type": "int_min", "min": 0 }
    ],
    "outputs": [
      { "name": "item", "type": "item_count" },
      { "name": "health", "type": "int_min", "min": 0 }
    ],
    "body": [
      {
        "condition": "item > 0",
        "modify_stats": { "item": -1, "health": 25 }
      }
    ]
  }
]
```

Call from a choice (`next_scene` is the **return target**; use the same
scene id to stay in place):

```json
{
  "text": "Выпить зелье",
  "next_scene": "start",
  "condition": "potion > 0",
  "call": {
    "subroutine_id": "drink_potion",
    "args":    { "item": "potion", "health": "health" },
    "outputs": { "item": "potion", "health": "health" }
  }
}
```

### Local frame

- A call creates a private `PlayerState`-backed frame. `inputs` are copied
  **into** it; `outputs` start at their type defaults and are copied
  **out** on return.
- A name in both lists is an **in-out** parameter: it starts with the
  caller's value and is written back; the types must match.
- The body sees **only** its own inputs/outputs. It cannot read or write
  `Adventure.variables` directly. Anything needed must be passed in as an
  input; anything changed must be exposed as an output. This is what makes
  a subroutine a predictable contract.
- On a choice, argument sources and output targets are global variable
  names. Inside a body they are names of the enclosing frame's locals.
- Every declared **input** must be mapped in `args`. An **output** may be
  omitted from the call's `outputs` map; its value is simply discarded.
  Unknown output names and missing/extra inputs are compile errors.

### Flat guarded steps

`SubroutineStep` is a flat list, not a nested `if` tree:

1. If `condition` is present and false, skip the step.
2. Apply `effects` to the frame in order.
3. If `call` is present, push a nested frame. On return, the child's
   outputs are written into the parent's locals; the parent resumes at the
   next step.

An `else` is the next step with the negated condition. The editor is a
flat table of rows (condition + effects + optional call). There are no
loops, nested control flow or arbitrary local variables in N6.base; those
belong to Ф13 `Procedure`.

### Call/return stack

Nested calls use an explicit frame stack. Outputs are copied into the
parent frame; the top-level frame writes into global state. Recursion is
**not allowed**: `Engine.compile` rejects a cyclic call graph
(`CompileError.SubroutineCycle`), and the runtime has an additional
`MAX_DEPTH` guard against hand-built IR.

### Validation split

| Layer | Checks |
|---|---|
| Parser (`JsonToIr`) | blank ids/names, duplicate parameter names, in-out type mismatch, unparseable conditions, blank call ids/arguments |
| Compile (`Engine.compile`) | unknown subroutine ids, missing/extra input args, unknown output names, duplicate ids, call-graph cycles |
| Type checker | top-level args/targets against globals, nested args/targets against the local frame, input-only writes, `ItemList` params (unsupported), call arg/output type mismatches; body errors are wrapped in `TypeError.InSubroutine` |
| Runtime (`SubroutineExecutor`) | structural failures → `RejectReason.SubroutineFailure` (compile should have caught them) |

**Not supported in N6.base:** `ItemList` parameters, loops, arbitrary
locals, parameterized effect deltas, recursion. The common in-out pattern
(`item > 0` → `item -= 1`, `health += 5`) is fully supported.

### A subroutine does not control button availability

The button is enabled/disabled by the **choice's** `condition`, not by the
subroutine's internal guard. If "drink potion" should be disabled when the
player has no potions, put `"condition": "potion > 0"` on the choice. The
subroutine's `item > 0` still protects the effects when called from
another context, but it does not grey out the button.

## How the four features compose

- **Template:** expanded at authoring time into an ordinary choice. The
  runtime sees expanded `text`/`condition`/`visibilityCondition`/`effects`.
  `template_ref` is metadata.
- **Visibility/condition:** evaluated by the UI (`ChoiceState`) and, for
  `condition`, by `Engine.step` (authority). Hidden is UI-only.
- **Merge:** a scene property; it does not change the transition. The
  branch effects are already in the arriving `PlayerState`.
- **Subroutine:** runs after choice effects, before invariants and the
  transition. Its outputs are part of the post-step state, so
  `disabledChoices`, invariants/death and the target scene all see them.
- A hand-edited/expanded choice may carry both `template_ref` and `call`:
  `template_ref` is ignored by the runtime, `call` executes normally.

## Error catalogue (choice-related)

| Error | Layer | Meaning |
|---|---|---|
| `ParseError.Structure` | parser | blank/duplicate/structural JSON problems (choice text, template params, subroutine params, blank call ids) |
| `CompileError.MissingNextScene` | compile | `next_scene` target does not exist |
| `CompileError.MissingMergeSource` | compile | declared merge source does not exist |
| `CompileError.MissingSubroutine` | compile | call references an unknown subroutine |
| `CompileError.InvalidSubroutineCall` | compile | missing/extra input args or unknown output name |
| `CompileError.SubroutineCycle` | compile | recursive/cyclic subroutine calls |
| `TypeError.UnknownVariable` | type check | name not declared in the relevant scope (global or subroutine frame) |
| `TypeError.InvalidSubroutineSignature` | type check | duplicate/in-out mismatched params, `ItemList` param, input-only write, call arg/output type mismatch |
| `TypeError.InSubroutine` | type check | wrapper adding the subroutine id to a body error |
| `LintKind.MergeConflict` | analyzer | `NoIncomingBranches` / `SourceDoesNotLeadHere` / `SourceNotReachable` |
| `LintKind.UnreachableScene` / `DeadEnd` | analyzer | reachability / terminal-scene warnings |

`Engine.compile` errors prevent opening/playing the file. `TypeError`s
prevent a successful parse (the editor shows them in "Проверить").
`LintKind` issues are warnings/one error (`EndingSceneWithChoices`) that
do not change the core transition model.

## Reference sample

`app/src/main/res/raw/test_adventure.json` exercises all four constructs
and is the source of `engine/src/test/resources/golden_ir.json`:

- `choice_templates.rest` used in `start`, `health_test`, `items_test`;
- disabled choice in `items_test` (`condition: "potion >= 2"`);
- `merge_test` with `merge_sources: ["health_test", "items_test"]`;
- `drink_potion` (called from two scenes) and `drink_potion_strong`
  (a second variant);
- visible/hidden template choice via `visibility_condition:
  "health < 100"`.

The editor labels the mechanisms explicitly: "Из шаблона: rest",
"Подпрограмма (необязательно): …", and the scene badge "🔀 Слияние".

## Versioning

None of these four features bumped `Adventure.CURRENT_VERSION` (still
`5`). All new fields are optional with empty/false/null defaults and an
identity migration:

- `choice_templates` — Ф4.1;
- `visibility_condition` — Ф4.2;
- `merge` / `merge_sources` — Ф4.5;
- `subroutines` / `choice.call` — Ф4.7;
- parser/editor support for `template_ref` and `visibility_condition` —
  Ф4.10.

Existing files without these fields behave exactly as before.
